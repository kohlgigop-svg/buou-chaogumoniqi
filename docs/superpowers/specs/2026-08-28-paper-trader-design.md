# 模拟炒股游戏《大布偶证券交易所》设计规格（paper-trader）

- 日期：2026-08-28
- 状态：已与需求方逐节评审通过（6/6 节），本文为汇总规格
- 范围：第一版（V1）完整功能 + 部署；二期候选单列

---

## 1. 项目概述

一个多人在线模拟炒股网页游戏。行情为**纯模拟**：虚构股票池 + 真实 A 股规则 +
随机过程引擎，不接入真实行情数据，不使用真实公司名称。玩家注册即得初始资金
¥100,000，通过交易、打工、能力养成与贷款经营自己的资产，参与排行榜竞争。

**设计原则**
1. 服务端唯一权威：一切数值由服务端计算，客户端输入一律经校验。
2. 账实相符：所有资金变动走只追加流水（ledger），恒等式受测试保护。
3. 规则真实：A 股核心规则逐条照搬（见 §5）；虚构的只有标的与行情本身。
4. 数据驱动：全部平衡数值集中于 config 与 seed 数据，改数字不改代码。
5. 体量务实：目标并发几十人，架构按此裁剪（单进程 + SQLite），不过度设计。

**非目标（V1 不做）**：融资融券（做空）、打新申购、持仓质押贷、玩家间转账、
实操小游戏打工、期权期货、邮箱验证/找回（已明确取消）、原生 App。

## 2. 时间体系（全局唯一时钟）

| 常量 | 值 |
|---|---|
| 1 游戏交易日 | 60 现实分钟 |
| 换算 | 1 现实分钟 = 24 游戏分钟；8 游戏小时 = 20 现实分钟 |
| 交易日编号 | 从创世时刻（`GENESIS_TS`，环境变量）起连续编号 1,2,3…，无周末 |
| 引擎 tick | 3 现实秒（连续竞价时段每日约 1100 tick） |

**每交易日结构（现实分钟）**：开盘集合竞价 3 → 连续竞价 55 → 收盘集合竞价 1 →
日终结算 1。

**日终结算窗依序执行**：成交/委托日终清理（未成交委托自动撤销）→ T+1 持仓解冻 →
贷款计息与逾期推进 → 工资/课程结转 → 财报披露与分红除权 → ST/退市/IPO 状态推进 →
信誉更新 → 全服对账（§16 不变量）→ 自动备份 → 生成次日事件与种子。

**停机补跑**：引擎状态（当前日/相位/tick 序号/PRNG 状态/市场状态）每 tick 落盘。
进程重启后按墙钟计算应到达的 tick，用持久化种子**确定性补跑**全部错过的
tick（含撮合与日终结算）。补跑结果与不间断运行逐字节一致（受测试保护）。
玩家在停机期间的挂单照常参与补跑撮合。

## 3. 系统架构

单 Docker 容器、单 Node.js 进程、三层：

```
┌─────────────────────────────────────────────┐
│  Node.js 22 (TypeScript)                    │
│  ┌────────────┐  ┌───────────────────────┐  │
│  │ 行情引擎    │→│ Fastify API + WebSocket │←── 浏览器 (React SPA)
│  │ (tick 循环) │  │ + 静态文件托管          │  │
│  └─────┬──────┘  └──────────┬────────────┘  │
│        └──────┬─────────────┘               │
│        ┌──────▼──────┐                      │
│        │ SQLite(WAL) │  挂载持久卷 /data     │
│        └─────────────┘                      │
└─────────────────────────────────────────────┘
```

- 引擎与 API 同进程，通过内存直调；better-sqlite3 同步事务保证撮合原子性。
- 单进程即全局撮合串行化，天然无竞态；体量（几十人）远低于 SQLite 上限。
- 前端构建产物由 Fastify 托管，同源部署，无 CORS。

## 4. 行情引擎

### 4.1 股票池

**110 只**虚构股 + 综合指数（市值加权，基点 3000）+ 20 个板块指数（基点 1000）。
完整清单见附录 A：沪主板 56 只（`60xxxx`，±10%）、深主板 40 只（`00xxxx`，±10%）、
创业板 14 只（`30xxxx`，**±20%**）。名称为真实龙头的戏仿（如"黔台酒业"），
代码避开真实知名代码。每股 seed 数据含：总股本、初始价、波动档、β、派息倾向。

> ⚠️ **2026-09-15 扩容（48 → 110）**：`STOCK_SEEDS` 与 `cfg.market.poolTarget`
> 必须**同时**改。老库（线上）靠 `ensureStockSeeds()` 幂等补齐，且**必须修正指数
> 除数** —— `mcapOf('COMP')` 是全市场市值之和，凭空多 62 只股会把指数从 3000 点
> 顶到 5857.9 点（实测）。bootstrap 的补齐是「流程外的成分变化」，`settlement.ts`
> 第 6→9 步那套 mcapBefore/mcapAfter 覆盖不到它，所以修除数只能由 topup 自己做。
> 另注：新股的 `listed_day` 必须写 `1`（写当天会被 `limitKindOf` 判成 IPO 首日档
> +44%/−36%）。

### 4.2 价格模型（每 tick，对数收益叠加）

```
r_stock = β·r_market + γ·r_sector + ε_idio + J_event + κ·(lnV − lnP)/D + I_player
```

| 项 | 定义 |
|---|---|
| `r_market` | 大盘因子：三状态隐马尔可夫（牛/震荡/熊），日级小概率转移（转移矩阵在 config），决定当日漂移与波动放大系数；日内为带漂移的高斯步 |
| `r_sector` | 板块因子：低幅度 AR(1) 共同冲击，γ 默认 0.5–0.8 |
| `ε_idio` | 个股特质噪声：学生 t 分布（ν=4，肥尾），σ 按附录 A 波动档校准 |
| `J_event` | 事件冲击：新闻/财报的即时跳变 + 数日衰减漂移（§4.3） |
| 锚定项 | `V` 为隐藏内在价值（EPS × 行业市盈率过程），κ 小、D 为回复期（日级）；保证长期不脱离基本面 |
| `I_player` | 玩家冲击：玩家净买卖流引起的临时冲击（随 tick 衰减）+ 小比例永久冲击，λ·(净流量/日均量) |

价格四舍五入到 0.01 元；触及涨跌停即钉板（§4.5）。

### 4.3 事件与信息面

- **新闻**：泊松到达（全市场/板块/个股三级，日均次数在 config）。类型库共 30 种
  （附录 B），各带冲击分布（对数收益区间）与衰减天数。新闻先推送标题，冲击在随后
  3–10 个 tick 内逐步释放——读新闻抢单是有效策略。

> ⚠️ **2026-09-15：`impact_e6` / `drift_days` 绝不下发到客户端。**
> 这两个字段是**模型内部的冲击强度**，等于把答案印在新闻上：新闻在 `tick ∈
> [60,1159)` 到达，而冲击要经 `eventRelease`（instant 30% + 9 个 tick 摊释 +
> `driftDays` 日衰减）才释放完。玩家看到"+5.2%"就知道该买什么——那不是看新闻，
> 是读答案。故 `/api/news` 与 `/api/stocks/:code` 的 news 子查询都**不再 SELECT**
> 这两列（DB 里仍存，引擎要用），只下发 `related`。
>
> **`related` = 新闻旁的关联标的实时行情快照**，不是预测。真实行情终端（同花顺/
> 东方财富/Wind）挂在新闻旁的也是这个，而非涨跌预测。三种口径：
> `STK` → 该股 `chgPct`（`code` 可跳转）；`SEC` → 板块内 `chgPct` 简单平均
> （`code: null`）；`MKT` → 大盘指数涨跌（`code: 'IDX:COMP'`）。标的已退市时
> `related = null`，前端**整段不渲染**（`web/src/components/NewsRelatedTag.tsx`）。
> 新闻板块已升为一级导航项（§11）。
- **财报**：每股每 60 交易日一期，披露日按股票错开。披露前 5 个交易日进入"财报
  日历"（全站可见）。财报 = 隐藏基本面 EPS 的带噪观测；`surprise = 披露值 − 市场
  预期（上期外推）`，披露时按 surprise 比例跳变并带 1–3 日漂移。
- **确定性**：所有随机数出自持久化种子的 PRNG（xoshiro128**；主种子 + 日编号派生
  当日子流）。重启补跑结果一致。

### 4.4 盘口与撮合

- 玩家为价格接受者，NPC 合成流动性。**五档盘口**由引擎按流动性参数围绕现价合成，
  玩家未成交限价单真实并入对应档位显示。
- **市价单**：按现价 + 冲击滑点成交；滑点 = k·√(委托量/该股日均量)，向不利方向取整
  到分。小单无感，大单有感。
- **限价单**：入队，现价穿越委托价即成交（价格优先、时间优先的简化实现：同价位
  按提交 tick 排序）。
- **集合竞价**（开盘 3 分钟/收盘 1 分钟）：仅接受限价单，可挂撤；以"模型参考价 +
  玩家净需求失衡调整"产生单一成交价，可成交委托按该价撮合；未成交限价单转入
  连续竞价（收盘竞价后未成交则日终撤销）。
- **成交回报**：经 WebSocket 即时推送（含逐笔费用明细）。

### 4.5 涨跌停钉板

- 涨跌停价 = 昨收 ×(1±幅度)，四舍五入到分。
- 封板期间：对手方向委托即时成交；同方向委托排队，每 tick 以时间优先 + 概率放量
  部分成交（模拟"涨停买不进、跌停卖不出"）；板上概率与封单强度参数在 config。

## 5. 交易规则（照搬 A 股）

| 规则 | 取值 |
|---|---|
| 交易单位 | 买入 100 股整数倍；卖出可零股（送转碎股可一次卖出） |
| T+1 | 当日买入次日可卖（日终解冻）；卖出资金当日可用 |
| 涨跌停 | 主板 ±10%，创业板 ±20%，ST ±5%，IPO 首日 +44%/−36% |
| 佣金 | 成交额万 2.5，最低 5 元，双向 |
| 印花税 | 成交额 0.05%，仅卖出 |
| 过户费 | 成交额万 0.1，双向 |
| 委托 | 限价单/市价单；当日有效；可撤单；集合竞价时段仅限价单 |
| 幂等 | 下单携带 clientKey，重复提交去重 |
| 取整 | 各项费用逐笔四舍五入到分；价格最小变动 0.01 元 |

**资金冻结**：限价买冻结 `价×量+费用上限`，成交按实际费用清算并释放多余冻结；
市价买按现价上浮 2% 缓冲冻结，未成交部分即时释放。卖出冻结持仓股数。

**资产口径（全站唯一）**：总资产 = 可用资金 + 冻结资金 + 持仓市值 − 未偿贷款本息。
排行榜、杠杆约束、强平、破产判定均用此口径。

## 6. 公司生命周期

- **分红**：财报盈利公司按派息倾向（附录 A：高/中/低/无 → 派息率 60%/30%/10%/0，
  基数为该期 EPS）于财报日 +3 交易日除息：昨收基准价下调、现金红利扣 **10% 红利税**
  入账并记流水。
- **ST**：连续 2 期财报亏损 → 戴帽（±5%，全站公告）；摘帽条件：连续 2 期盈利。
- **退市**：ST 后再亏 1 期或净资产为负 → 进入 20 交易日退市整理期（全程标示），
  到期摘牌，持仓按最后价 **30% 现金回收**（记流水）。
- **IPO**：有股摘牌即触发（另有低概率随机 IPO），同行业新股上市补池，池子恒约
  **110 只**（`cfg.market.poolTarget`）。首日 ±44%/−36%，次日起按板块正常幅度。
  V1 无打新，首日直接可买。

## 7. 账号与安全

- 注册：用户名（2–16 字符，唯一，允许中英文数字下划线）+ 密码（≥8 位）。
  argon2id 哈希。每 IP 每日最多注册 5 个；登录失败 5 次/15 分钟锁定。
- 会话：服务端会话表 + HttpOnly/SameSite=Lax/Secure Cookie，30 天滑动过期，可踢下线。
- 初始资金 ¥100,000，注册即记 ledger 第一条（type=GENESIS）。
- 无邮箱体系；忘记密码 → 管理员后台重置（§15）。
- 防护：zod 全接口入参校验、@fastify/rate-limit 速率限制、参数化 SQL、
  自定义请求头 + SameSite 防 CSRF、服务端全权威。

## 8. 信誉系统（350–850，初始 600）

| 事件 | 变动 |
|---|---|
| 按期还清一笔贷款 | +15 |
| 提前还清一笔贷款 | +20 |
| 逾期中 | 每交易日 −8 |
| 被强制平仓 | 一次 −80 |
| 破产 | 直接置为 400 |
| 完成打工班次 | +1（每 20 交易日经此途径最多 +10） |

信誉的作用：贷款额度与利率档位（§9）、逾期/强平状态全站禁止新贷款与高薪岗

## 9. 贷款系统（NPC"布偶银行"）

**产品**：信用贷。期限档 20/60/120 交易日；单利，每交易日结算计提利息；到期一次
还本；支持随时部分/全额提前还款（还款先冲抵已计提利息，再冲本金）。

**额度与利率查表（按申请时信誉分）**

> ⚠️ **2026-09-15 起「授信上限」一列已废弃**，改为**公式**：
> `额度 = 信誉分 × cfg.loans.capPerCreditPoint`（默认 `500_000` 分 = ¥5,000/分，
> 即「个人信誉分 × 5000 元」）。信誉 600 → **¥3,000,000**。
> 下表**只有「日息」一列仍然有效**（`cfg.loans.tiers` 现为 `[minScore, rateE6]` 两列）。
> 另注：额度与总杠杆约束**都正比于信誉分**，故谁先拒只取决于净资产
> （额度 < 杠杆 ⟺ 净资产 > ¥1,500,000）；默认初始资金 ¥1,000,000 的玩家
> 实际被**杠杆**卡在 ¥2,000,000。

| 信誉区间 | ~~授信上限（未偿本金合计）~~ | 日息 |
|---|---|---|
| <500 | 拒贷 | — |
| 500–549 | ~~¥20,000~~ | 万 6 |
| 550–599 | ~~¥30,000~~ | 万 5.5 |
| 600–649 | ~~¥50,000~~ | 万 5 |
| 650–699 | ~~¥80,000~~ | 万 4.5 |
| 700–749 | ~~¥130,000~~ | 万 4 |
| 750–799 | ~~¥200,000~~ | 万 3.5 |
| 800–849 | ~~¥320,000~~ | 万 3.2 |
| 850 | ~~¥500,000~~ | 万 3 |

**总杠杆约束**（与授信额度取严）：未偿本息合计 ≤ 净资产 ×（信誉分 ÷ 300）。

> ⚠️ **「可借上限」是一个取严后的数，由服务端 `borrowRoom()` 唯一算出并下发**
> （`GET /api/bank/products` 的 `room`），前端**不得**自己用 `capCents − 未偿本金` 算。
> `room = min(授信剩余, 杠杆空间)`，`room.binding` 说明是哪条在卡。
>
> 为什么写进规格（2026-09-15 事故）：额度改成公式后，600 分玩家的**授信上限
> ¥3,000,000 超过了杠杆上限 ¥2,000,000**，而银行页当时只认 `capCents`，于是
> 「当前可用 ¥3,000,000」成了借不到的数字 —— 输入框留空时前端提交的正是它，
> **玩家点一下「借款」必然 403 LEVERAGE**。改公式之前额度上限 ¥50,000 恒小于
> 杠杆上限，UI 从不说谎，所以这条约束一直没被显式写下来。
> 现在「还能借多少」只有一处实现，UI 展示与放行闸门共用，不可能再漂移。

**逾期链条**：到期未还 → 宽限 3 交易日（罚息 2 倍利率）→ 逾期状态（每日 −8 信誉，
禁新贷款/高薪岗）→ 逾期第 10 交易日触发**强制平仓**：系统以市价单按持仓市值从大到
小逐笔卖出（滑点、费用照算，流水可查）直至清偿。

**破产**：强平后仍资不抵债 → 破产结算：剩余资产清零、债务豁免、信誉置 400、发放
救济金 **¥20,000**（非 10 万，防"梭哈失败重开"成为优势策略）、`bankrupt_count+1`
并在排行榜永久标注。

> **信用交易（融资融券）见 §21**。同为"借钱"，但风险口径完全不同：贷款是**固定
> 期限的现金负债**（看本金、看信誉分），融资融券是**随市价逐日盯市的担保负债**
> （看维持担保比例）。两者独立计额度、独立强平，但共享同一份现金与持仓。

## 10. 打工与能力

**能力 6 项**（各 0–10 级）：学历、编程、金融、体能、沟通、设计。

**课程升级**：Lv n→n+1 费用 `5000×1.6ⁿ` 元、时长 `(n+1)×8` 游戏小时（= (n+1)×20
现实分钟）。报名扣费并占用时间线；期间不可打工/报其他课，可交易；到点自动结业
（离线照常）。单项练满累计约 ¥90.8 万——高能力是长线投资。

**班次**：一班 = 8 游戏小时 = 20 现实分钟；可预约排队；**每游戏日最多开始 2 班**
（按班次开始时刻所属交易日计）；班次开始后不可取消，结束自动发薪并记流水。
上班期间不可上课/另开班，可交易。

**工资公式**：`实发 = 基础工资 × (1 + 0.05 × Σ超出该职业各要求项的能力点数)`。

## 13. 数据模型（SQLite，23 业务表）

`users`（含 cash_available/cash_frozen/credit/bankrupt_count/status）、`sessions`、
`stocks`（seed 参数）、`stock_state`（现价/昨收/涨跌停价/ST 状态/内在价值等）、
`candles_day`、`ticks`（滚动保留最近 3 交易日）、`orders`、`trades`（逐笔费用）、
`holdings`（qty_total/qty_sellable/**qty_margin**/avg_cost）、`ledger`（只追加，含
balance_after）、`loans`、`credit_events`、`jobs`、`shifts`、`abilities`、
`enrollments`、`news`、`reports`、`dividends`、`p2p_loans`、`login_attempts`、
**`margin_accounts`、`margin_positions`**（§21）共 23 张业务表；另有 4 张系统表：
`config`、`engine_state`（单行快照）、`announcements`、`admin_logs`。合计 **27 张**，
最终以迁移脚本为准。

约束要点：ledger append-only（无 UPDATE/DELETE）；orders/trades 外键完整；
holdings 非负；所有金额以"分"为整数存储，展示层转元。

> ⚠️ **`holdings.qty_margin`（2026-09-15 新增）**：融资买入的股票**仍然记在
> `holdings`**（分红 / 退市回收 / 估值 / T+1 全部沿用既有路径），靠这一列标记
> "其中多少股是交给券商的担保物"。不变式：`qty_total === qty_sellable + qty_margin`。
> **日终那句解冻必须同步改** —— `matcher.onDayEnd` 原为
> `UPDATE holdings SET qty_sellable = qty_total`，必须改成
> `qty_sellable = MAX(0, qty_total − qty_margin)`，否则担保股票次日被解锁成可卖，
> 等于让玩家把券商的抵押品卖掉。（已由 `server/test/domain/margin.test.ts` 钉住：
> 临时改回旧写法恰好红一条。）
>
> ⚠️ **`margin_accounts.debt` / `margin_positions` 不进 ledger**：ledger 记的是
> **现金流向**，不是债权。融资放款那天 `BANK −X / user +X` 是唯一的记账点；日后
> 还款另有一条 `user → BANK` 的现金腿；**豁免债务只改这两张表、不记账**，故不会让
> `auditGlobal`（要求全局 Σ = 0）失衡。同理，`ledger.bucket` 只有 `'A'/'F'`，**不
> 为信用账户另开现金桶** —— 凭空造一个"信用账户现金"会让 `auditUser` 的
> 「Σ ledger(A) === users.cash_available」勾稽失守。所有资金仍在这两个桶里流转。

## 21. 融资融券（信用交易，2026-09-15 新增）

> 原为 §19 二期候选，本版落地。与 §9 银行贷款是**两套东西，不要互相套用**：
> `loans` = 无抵押信用贷，钱到手随便花，按信誉分定额度；
> `margin` = **有担保的杠杆交易**，钱只能买指定标的，且**随市价逐日盯市**。

### 21.1 规则（照搬 A 股）

| 项 | 取值 | 说明 |
|---|---|---|
| 开通门槛 | 信誉分 ≥ **650**（`margin.minCredit`） | 幂等，重复开通不报错 |
| 保证金比例 | **50%**（`initRatioE6`） | ⇒ 最高 **2 倍**杠杆 |
| 融资日息 | **0.02%/日**（`financeRateE6`） | 按**本金**计提 |
| 融券日费率 | **0.025%/日**（`shortRateE6`） | 按**融券市值**计提 |
| 融资负债上限 | 信誉分 × **¥2,000/分**（`maxDebtPerCreditPoint`） | 600 分 → ¥1,200,000 |
| 单笔最小金额 | ¥1,000（`minOrderCents`） | |
| 警戒线 | **150%**（`warnRatioE6`） | 跌破 ⇒ **不能再开新仓** |
| 平仓线 | **130%**（`liqRatioE6`） | 跌破 ⇒ 追保，**T+1 未补足即强平** |

**维持担保比例** = （现金 + 全部持仓市值）/（融资负债本息 + 融券市值）。
无负债时为 `null`（不是 0、也不是 Infinity —— 前端要能区分，`ratioPct(null) → '—'`）。

**两个开仓动作**

- **融资买入**（看多，`POST /margin/finance`）：成交金额 `A` 中自有保证金 = `A × 50%`，
  券商借出 `A − 保证金`。开仓后维持担保比例 = **200%**。
- **融券卖出**（做空，`POST /margin/short`）：**卖出所得全额冻结**，另需自备同比例的
  保证金；两者都冻结在 `F` 桶。开仓后维持担保比例 = **150%**。

> ⚠️ **融券保证金必须含卖出费用**（`marginUsed = A×50% + fees`）。卖出所得是**扣费后**
> 的净额，若不把费用补进保证金，开仓瞬间比例 = `(0.5A + A − fee)/A ≈ 149.9%`
> —— **低于 150% 警戒线**。后果不是数字难看，而是玩家一开仓就再也开不了第二笔，
> 偏偏此时账上现金已经见底，只能干等股价下跌。补上费用后冻结额 = 净额 + 保证金
> = `1.5A`，开仓瞬间正好 150%（已由测试钉住 `ratioE6 === 1_500_000`）。

**三个平仓动作**

- **卖券还款**（`POST /margin/sell-repay`）：卖出担保股票，所得**先息后本**冲抵负债，
  剩余留在可用现金。不足部分不追缴（负债继续按日计息）—— 这是玩家主动降杠杆的主要手段。
- **买券还券**（`POST /margin/buy-cover`）：买回等量股票还券，资金优先来自该笔空头
  冻结的担保金（按 `frozen × 还券量 / 持仓量` 比例解冻），不足部分由可用现金补。
  **股票涨了就可能要倒贴现金 —— 这正是做空的风险。**
- **直接还款**（`POST /margin/repay`）：现金 → 券商，先息后本。追保时把比例抬回去的
  主要手段之一。

### 21.2 日终结算（`MarginSettlementHook`，每交易日三步）

1. **`reconcile` 对账** —— 让 `margin_positions` 与 `holdings` 保持一致。
   为什么需要：有两条路径会**绕过信用交易**去动担保股票 ——
   ① `processDelistings` 直接 `DELETE FROM holdings` 并折成现金；
   ② `LoanSettlementHook` 的破产清仓会把该用户**全部**持仓卖光（含担保物）。
   两条都是别的模块的职责，不该在那里塞融资融券的分支；这里做一次幂等收敛即可
   （只会把仓位往"实际持有"上夹）。退市空头的冻结资金全额解冻还给玩家
   —— 把公司做退市，空头赚满。
2. **逐日计息** —— 融资按本金 × 日息；融券按**市值** × 日费率（退市券不计）。
3. **维持担保比例检查** —— 跌破平仓线记下 `warn_since_day`，**`ctx.day > warnSinceDay`
   才强平**（T+1 追保）。补足后 `warn_since_day` 清零。

> ⚠️ **钩子顺序：`marginHook` 必须排在结算钩子链的最后一个**（`index.ts` 的
> `settlementHooks: [loanHook, workHook, p2pHook, marginHook]`）—— 它要读**本日收盘价**
> 算比例，而前面的钩子会改现金与持仓。另外 `matcher.onDayEnd` 在钩子之前跑，
> 所以此刻 `F` 桶里只剩融券担保金（挂单冻结已全部释放），强平买回时不会误用别人的挂单资金。

**强制平仓（`liquidate`）四步**

1. 多头全部卖出（`forceSell`）：不走订单簿，按**现价 ×(1−滑点) 与跌停价孰高**成交。
2. 空头全部买回（`forceBuy`）：**绝不能因为现金不足而抛错** —— 抛错会让整个 tick
   事务回滚、结算卡死。做法是允许券商**垫付**：缺口由 `BANK` 直接划给用户
   （系统账户可为负），同时等额记进 `debt`，于是「空头爆仓」被平滑转成
   「欠券商一笔钱」。这既符合现实（券商代垫后向投资者追偿），也避免「买不回来就
   永远挂着」的死结。
3. 用全部可用现金冲抵负债（先息后本）。
4. **仓位全平完才豁免残债**（`debt = interest = 0`）—— 否则会出现「债务清了、空头
   还在」的无担保敞口。还有仓位没平掉（券源买不回来等）就保留残债，下一个交易日
   再处理。最后记一次信誉事件 `MARGIN_FORCED_LIQ`（`cfg.credit.forcedLiq`，−80）。

### 21.3 三处「不这么做就出事」的实现约束

> ① **担保物口径 = 全部现金与持仓，不是只算信用持仓**。本游戏不把信用账户与普通
> 账户分家 —— `ledger.bucket` 只有 `'A'/'F'` 两桶，另开一个「信用现金」桶会让
> `auditUser` 的勾稽（Σ ledger(A) === `users.cash_available`）失守。钱是同一个口袋
> 里的，担保物也只能按同一个口袋算。副作用是「净资产越大越不容易被强平」，与现实
> 一致（现实里也可以随时往信用账户补钱），且被 `maxDebtPerCreditPoint` 从绝对额兜住。
>
> ② **债务不进 ledger**。ledger 记的是**现金流向**，不是债权。融资放款那天
> `BANK −X / user +X` 是唯一的记账点；日后还款另有一条 `user → BANK` 的现金腿；
> **豁免债务只改表、不记账**，故不会让 `auditGlobal`（要求全局 Σ = 0）失衡。
>
> ③ **`valuation.totalAssets` 必须扣 `marginDebt`**（= `debt + interest` + 融券市值）。
> 否则融资买入会让股票进 `positionsValue`，而借来的钱只记在 `margin_accounts.debt` 里
> ⇒ 净资产凭空虚高 ⇒ 银行杠杆上限（净资产 × 信誉分/300）跟着虚高 ⇒
> **可以拿信用仓当抵押去银行套更多贷款**。`portfolio.ts` 的 `Valuation` 因此新增
> `marginDebt` 字段。

### 21.4 交易记录与系统单

融资买入/融券卖出/强平都**不走订单簿**，但 `trades.order_id` 是
`NOT NULL REFERENCES orders(id)`，所以每次直接成交都要先补一张
`type='M'`、`status='done'` 的系统单。`client_key` 由 `systemClientKey(db, tag)`
取「当前 `MAX(orders.id) + 1`」生成 —— `orders` 有 `UNIQUE(user_id, client_key)`，
而强平可能在同一 tick 对同一只股票连续下多张单，不能用「日期+股票」这种粗粒度键
（`orders` 行从不删除，故跨事务也不会撞）。

**错误码**（前端文案在 `web/src/errors.ts`）：`MARGIN_NOT_OPEN`（未开通）、
`MARGIN_CALL`（低于警戒线，禁开新仓）、`MARGIN_LIMIT`（超融资负债上限）、
`POSITION_NOT_FOUND`（没有这笔信用持仓）、`NOTHING_OWED`（无债可还）、
`BAD_CODE`（标的不可交易）、`BAD_QTY` / `BAD_AMOUNT`（数量或金额非法）、
`CREDIT_LOW`（信誉分不足开通）、`INSUFFICIENT_CASH`（现金不足）。

### 21.6 ⚠️ 删号必须连带清理信用表（否则结算卡死）

`margin_accounts` / `margin_positions` **没有**指向 `users` 的外键（故意的：
债务不是现金流向，不参与 ledger 勾稽）。代价是**漏删不会报错**，只会留下孤儿行。

而日终结算的 `checkMaintenance` 会遍历 `margin_accounts`，对每行调 `marginState()`
—— 它第一件事就是读 `users.credit`。**用户不存在即抛 `UNAUTHORIZED`，把整个 tick
事务带崩。** 线上表现是「结算卡死、行情停摆」，日志里只有一句 401，
极难联想到是几天前删了个号。

两层防护（都要有，都是幂等的）：

1. **`DELETE /api/admin/users/:id` 在删 `users` 行之前删这两张表**，
   并把「未平信用持仓 + 未偿信用负债」计入 `blockers`（`openMargin`）——
   只算持仓会漏掉「已卖光担保股票但还欠券商钱」这种形状。
2. **`MarginSettlementHook.reconcile` 兜底清理孤儿行**（管旧账、管半删状态）。

只删 margin 两张表，**绝不动 ledger**（append-only，全局平衡靠它）：债务本就不进
ledger，所以「删号即债务消失」不会让 `auditGlobal` 失衡。

> 复现与回归：`server/test/domain/margin.test.ts` 的「孤儿账户不能把结算带崩」
> （直接删 `users` 行、保留 margin 行，断言结算不抛错且孤儿行被清掉）与
> `server/test/api/market-admin.test.ts` 的「DELETE 必须清理融资融券从属行」
> （3 例）。修复前这 4 例全红，其中两例的报错正是 `Error: not logged in`。
